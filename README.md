# 歌曲評審團(song-jury)

[![CI](https://github.com/vava2684/song-jury/actions/workflows/ci.yml/badge.svg)](https://github.com/vava2684/song-jury/actions/workflows/ci.yml)

> 🎧 **免安裝線上試用**:**https://meowfullhouse.com** → 點「免費歌曲評審團」,貼 SUNO 連結即評。
> 想自架 / 進階功能(PK、抽卡比較)看以下。

一套本機跑的 **AI 歌曲評測系統**。不需要參考原曲,從九個主題角度給出可辯護的診斷 ——
**它替評審完成 80% 的細部研究,最後 20% 的判斷永遠屬於人。**

**為什麼可信**:這套系統的每一個權重、每一次除名、每一條凍結,都出自**十三個不同模型家族的正式辯論程序**
(Anthropic / OpenAI / Google / xAI / DeepSeek / 阿里 / Moonshot / MiniMax / Mistral / NVIDIA / Meta / 百度 / 騰訊),
有票數、有判準、有紀錄 —— 完整沿革見 [`docs/權重沿革.md`](docs/權重沿革.md)。
分數是**診斷分**:同標準下排序、定位問題用,不自稱客觀真理。**終審是聽眾。**

## 九柱制(滿分 100)

```
總分 = 25.3%×詞柱 + 74.7%×曲側八柱
```

| 柱 | 權重 | 評什麼 | 誰在評 |
|---|:--:|---|---|
| ✍️ **詞** | 25.3% | 歌詞(中/英/日/韓四把語言尺,作品分/爆款分雙分) | 對話中的 AI 依尺執行 |
| 🎤 **人聲演唱** | 15.2% | 唱得好不好 | 演唱量測 + SingMOS 聽感 + 兩隻模型耳 |
| 🎼 **和聲** | 13.6% | 和弦寫作:終止式/和弦詞彙/調性/五度動線/延伸和弦 | Viterbi 和弦辨識 |
| 🏗 **結構與編曲** | 12.6% | 能量成長、編制變化、結構弧線、配器 | Demucs 六軌 + 模型耳 |
| 🔊 **聲學製作** | 12.1% | 混音品質:頻譜/立體聲/諧波/動態 LRA | EBU R128 量測 + Audiobox |
| 🎵 **旋律與記憶** | 6.1% | 旋律好不好記 | Gemini + SongEval |
| 🌍 **真實性與風格** | 6.1% | 離真實專業音樂多遠、曲風有無新意 | MuQ 嵌入距離 + Gemini |
| 🧭 **整體音樂性** | 5.1% | 聽完整首的總體感 | Gemini + SongEval |
| 🥁 **律動** | 4.0% | 節奏活不活 | Gemini |

**柱外三種項目**(照列不計分,誠實攤開):
**顯示軸**(AI 感偵測、編曲細部、Reach 訊號)、**體檢**(響度/削波,異常才出聲)、
**❄ 凍結**(可靠性驗證未過的量測,分數照列標 ❄ 不計入)。

> **為什麼按主題分柱而不按模型分**:同一個主題裡,**量測給數字、模型給耳朵,互為證據鏈**。
> 兩邊吵架時報告會攤開讓評審自己判 —— 這正是它想被使用的方式。

## 三種輸入 · 三種模式

| 輸入 | 說明 |
|---|---|
| **SUNO 連結**(`suno.com/song/…` 或 `/s/`) | 自動下載歌 + 抓歌名/歌詞 |
| **YouTube 連結** | 自動下載歌(需 yt-dlp+ffmpeg);抓不到詞請另給 |
| **本機檔案** | 音檔路徑 + 歌詞(貼文字或 `.txt`) |

- **單評** — 只評一首,不與他歌比較
- **PK** — 多首並排排名;⛔ 僅限同語種、同計分契約、都要是完整九柱
- **重複抽卡比較** — 同一份詞+prompt 的多個 take 並排:該留哪一個、這套穩不穩

**PK 與抽卡的規則寫死在 `比較.py` 裡**(不是「由 AI 臨場編排」——那樣同一批資料
在不同對話會得出不同冠軍):

```bash
.venv\Scripts\python.exe 比較.py pk    --lang zh  甲_評審團.json 乙_評審團.json
.venv\Scripts\python.exe 比較.py takes --group A  t1_評審團.json t2_評審團.json t3_評審團.json
```

它先讓每份報告過獨立裁判(完整九柱、schema、合成自洽),再依**曲側合成**排名;
差距 <1.0 分標為並列(保守顯示規則,不是統計檢定 —— 系統沒有重複量測的變異數,
給不出真的信賴區間,這點寫在輸出的 note 裡)。抽卡模式比的是**曲側八柱全部**,
`best_take` 明確定義為曲側合成最高者,並報每柱落差與最不穩的那根柱。
⛔ 不同語言、不同 scoring contract、任一份不完整 → 直接拒絕比較(退出碼 2)。

**同一份評測不可以投兩次票**:報告會帶三種身分 ——
`evaluation_id`(這次評測)、`source_file_sha256`(**檔案 bytes**)、
`source_audio_pcm_sha256`(**解碼後的聲音**,保留原始取樣率與聲道結構,
另附 `source_audio_pcm_contract` 標明用哪一版標準面算的)。比較器據此拒絕
「複製一份改個名字」或「換個容器/改 metadata 再上場」當成兩首歌或兩個 take ——
那不必是惡意,整理檔案時順手複製就會發生,而結論會建立在同一份資料上。

⭐ **評測一開始就把來源固定成一份私有快照**,所有評分階段與兩種身分都只讀它
(Codex R23-P1-1)。⛔ 舊版是每個階段各自開「你給的那個路徑」、身分又在最後才另算
一次:評測中途檔案被換掉(同步軟體、剪輯工具另存、批次腳本覆蓋都會發生),就會產生
一份**分數來自 A、身分宣告 B** 的報告,而且退出碼 0、獨立裁判也照樣說合格。
快照會保留原檔名(只換目錄)——分軌快取的目錄名帶檔名前綴,改名會讓每次評測都重跑
Demucs。收工時快照連同目錄一起刪掉。
快照用 `copyfile` 複製(**不繼承唯讀屬性**)、收工時遇到唯讀會先 chmod 再刪並重試;
真的刪不掉(例如還有程式開著那個檔)會**大聲印出完整路徑**並以**退出碼 4** 結束 ——
⛔ 那是一整份音訊留在 TEMP,不可以沿用「一切正常」的退出碼無聲帶過(Codex R24-P1-1)。
建不出快照(空間不足/權限/路徑太長)會給一句人話,不是裸 traceback。
⚠️ 誠實邊界:這道防線處理的是**評測中途換檔**造成的不一致,不是防篡改 ——
同一個 OS 使用者本來就能改那份快照,那不在威脅模型內。

📁 **每一份暫存都有主人**(Codex R26-P1-1 / R27-P1):上傳檔沒有(或非小寫)音檔副檔名時,
產品會複製一份補正副檔名的音訊 —— 那份也走同一條契約(用完刪掉、刪不掉就講出來
並用退出碼 4)。⭐ 補正檔只當**內容來源**,報告仍寫在你原本的檔案旁邊,不會被寫進
TEMP 再跟著暫存一起消失;複製到一半失敗(磁碟滿/來源消失)時,
`resolve_input` 會**自己**先清乾淨再給人話 —— 那時候 main 的 finally 還沒進場
(Codex R27-P1-1)。`song_scorer.py --demucs` 產生的**完整分軌**同樣有主人:
交給呼叫端、由 main 的最外層 finally 清掉,demucs 自己失敗時就地清(R27-P1-2);
⛔ **確認真的刪掉了才放掉 owner**,刪不掉就印出完整路徑並以**退出碼 4** 收場
(正常收場含 `sys.exit(0)`;已經有例外在往外傳時只報告,不蓋掉原本的錯誤)——
Codex R28-P1-1 實測舊版會「目錄還在、卻沒有人負責」,或印了警告卻回 0。
`_stems/` 的 `.tmp_*`(寫到一半的整套分軌)也有同一套契約:寫入時持有鎖,
每次分軌前掃一次,**鎖拿得到而且夠舊**(預設 1 小時)才回收(R28-P2-3)。
⭐ 這四種暫存共用同一份實作 `暫存清理.py`(force_rmtree + OS 租約)——
規則各寫一份遲早有人漏掉一半。網頁版的歌詞與情感弧線圖則放進**產品自己的受管目錄**(`<狀態目錄>/web-tmp/`),
帶**租約**:請求開始時**持有一把 OS 鎖**(`.active`,Windows msvcrt / POSIX flock),
產物交給前端後放掉 —— 回收只清「鎖拿得到(= 沒有人在用)而且過了保留期
(預設 1 小時,`SONG_JURY_WEB_TMP_TTL`)」的目錄。
⛔ 沒有租約的話,一個跑很久的請求(情感弧線/本機詞評)會被下一個請求把正在用的
目錄刪掉,使用者拿到一張不存在的圖(Codex R27-P2-1 實測)。
⛔ 而租約也**不可以只是個檔案在不在的哨兵**(Codex R28-P2-1):那樣判死仍然靠牆鐘,
時鐘往前跳、機器休眠、或工作本來就比放棄期長(`SONG_JURY_WEB_TIMEOUT` 允許到 24 小時)
都會把還活著的工作誤判成孤兒。⭐ 用真的鎖之後:**鎖拿不到就不管多舊都不回收**,
而程序被砍時 OS 會自動放掉鎖,所以孤兒最後仍然收得掉。
⚠️ 誠實邊界:回收是**機會性**的(服務啟動時 + 每次請求),不是背景排程的時間保證;
清不掉會把完整路徑印出來,不會靜靜吞掉。⛔ 那可能是還沒公開的歌詞,
不可以靠「作業系統某天也許會清 TEMP」當生命週期。

算不出解碼身分時,報告會寫一份**明講原因**的降級宣告(Codex R22-P2-1)——
⛔ 欄位缺席有好幾種完全不同的意思(沒裝 ffmpeg、格式不支援所以**刻意**不發布、
解碼壞掉),只看「少了欄位」下游只能猜,實測比較器就把「s64 不支援」說成
「產出端沒有 ffmpeg,裝好重評即可升級」—— 叫人去做一件完全沒有用的事。

```json
"source_audio_pcm_status": {
  "status": "unavailable",
  "reason": "unsupported_sample_fmt",
  "generator_contract": "pcm-v5/native-rate/canonical-speakers/native-sample-fmt",
  "shape": {"sample_rate": "48000", "channels": "1", "sample_fmt": "s64", …}
}
```

⛔ 而且原因與 shape 必須**互相成立**(Codex R23-P1-2 / R24-P1-2):
`no_ffmpeg`/`probe_failed` 連 `shape: {}` 都不行(探測不到就寫不出來);
其餘三種一定要**寫齊六個欄位**(rate/channels/layout/sample_fmt/canonical/canonical_speakers),
rate 與 channels 必須是正整數,`canonical` 必須正好是**該樣本格式**對應的值、
`canonical_speakers` 必須正好是**該配置**算出來的值(裁判自己有一份 fmt→canonical 與
37 筆 layout→speakers 的表,有測試盯著它與產出端不漂移);在這個前提下再看原因:
`unsupported_sample_fmt` 的 canonical 一定是空的、`unknown_multichannel_layout` 一定是
3 聲道以上且算不出喇叭、`decode_failed` 則是前面每一關都過了。
少了這層關聯,「受支援格式卻沒算 PCM」只要換個殼寫成降級宣告就能繞過 strict ——
裁判是獨立的,不能假設 JSON 一定來自這版產出端。
⭐ 而**未知版本**(未來的 `pcm-v6…`)只驗結構、不套這一版的語意:它不會被當成證據
(strict 照樣擋),但也不會讓整份報告變不合法 —— 與解碼雜湊的政策一致,
否則「升級產出端」會變成破壞性事件(Codex R24-P1-2)。

於是**兩種政策**分得開(⛔ 不可以用一個布林代表兩件事):
`decoded`(安裝證據 `-VerifyModels`:demo 是 s16,算得出來才叫裝好)一律不接受降級;
`declared`(正式批次)接受「新版產出端明講算不出來」,但**受支援格式卻漏寫 PCM**
仍然照擋 —— 那是產出端迴歸,不是刻意降級。單獨驗一份報告時用
`--allow-declared-downgrade`,輸出會標成 `VERIFY_OK …;來源身分=宣告降級(原因)`。

輸出的 `source_identity.level` 誠實標出這批報告的證據強到哪裡:
`decoded-audio`(最強,換殼也認得出)→ `exact-file`(只認得同一個檔案 ——
產出端沒有 ffmpeg/ffprobe,或這批的解碼身分版本不一致時會這樣)→
`mixed` → `weak`(舊格式,只擋得掉完全相同的複製)。

⛔ 誠實邊界(都不假裝做得到):
> · **lossy 重壓**(320k→192k)會得到不同的聲音位元 —— 那需要 acoustic fingerprint;
> · **重新取樣或改聲道數**的版本會被當成不同來源 —— 解碼身分刻意保留原始取樣率與
>   聲道數,因為「先轉成 44.1k 立體聲再比」是**多對一**的,實測會把 48k 單聲道與
>   由它轉出的 44.1k 雙單聲道判成同一個來源(Codex R19-1);
> · **樣本格式也保留**:浮點來源解成 f64le、u8/s16/s32 才用 s32le ——
>   一律壓成 s32le 同樣是多對一,實測 1e-12 的浮點訊號會被量化成 0 而與靜音撞號、
>   超出滿刻度的 1.1 與 1.2 會被 clip 成同一個值(Codex R20-P1-1),
>   而 **s64 只差 1 個 LSB** 的兩段聲音也會被抹平(Codex R21-P1-1);
> · **s64/s64p 乾脆不發布解碼身分**:ffmpeg 沒有無損的 64 位整數 raw 容器
>   (只有 f64le,而 f64 的 53 位尾數裝不下 64 位整數)。⛔ 寧可沒有身分,
>   也不要一個會撞號的身分 —— 這種來源會誠實退到「檔案雜湊」那一層;
> · **不認得的樣本格式**同樣不發布身分(白名單,沒有 fallback):
>   ffmpeg 之後多一種格式時,fallback 會靜靜製造新的碰撞;
> · **喇叭配置吃語意、不吃字面值**:`channel_layout` 這個字串會隨容器漂移
>   (同一段 PCM 裝 WAV 被寫成 `unknown`、裝 MOV/CAF 寫成 `mono` —— Codex R21-P2-1),
>   但對多聲道它同時承載「第 N 個交錯聲道送去哪個喇叭」的語意。⛔ 上一版把它
>   **整個**踢出雜湊是矯枉過正:實測只改 WAV 的 `dwChannelMask`(5.1 後置 BL/BR
>   → 5.1(side) 側置 SL/SR)就會拿到同一個身分,比較器直接喊「這是同一首」
>   拒絕兩者同場(Codex R22-P1-1)。現在進雜湊的是**產品自己版本化的喇叭集合**
>   (= `ffmpeg -layouts` 的 DECOMPOSITION,有測試每次比對):
>   名字改版不影響身分,喇叭真的不同才不同;
> · **講不出喇叭配置的多聲道不發布身分**:3 聲道以上而 ffprobe 只說得出
>   `unknown` 時,硬補一個預設配置等於**製造**碰撞 —— 一律 fail closed。
>   (1/2 聲道沒有這種歧義,依產品規則補 `FC` / `FL+FR`,那正是換容器不漂移的來源。)
>   完整結構另外寫在 `source_audio_pcm_shape`(含 `canonical_speakers`)供稽核;
> · **跨 ffmpeg / decoder 版本不保證 bit-exact**:那個方向的失準是「算不出相同」
>   → 自動退回檔案雜湊那層,不會造出假的同源判定。換演算法就換
>   `source_audio_pcm_contract`,不同版本的雜湊**一律不互比**,
>   未知版本的雜湊**完全不採用**(不會被當成證據)。

> ⚠️ `examples/` 是四語各一首,依「禁止跨語言 PK」的規則**不能拿來 PK**;
> 要試 PK/抽卡請自備同語言多首、或同一份詞+prompt 的多個 take。

## 安裝

### 完全不懂電腦的話:雙擊一個檔就好

**先把專案抓下來**,兩種都可以:

- **不會用 git** → 在本頁按綠色的 **Code → Download ZIP**,解開就好(解出來的資料夾叫
  `song-jury-master`,可以自己改名)。**功能完全一樣** —— 程式不依賴 git,
  換行也已經處理好(`.sh` 是 LF、`.bat` 是 CRLF,有測試在守)。
- **會用 git** → `git clone https://github.com/vava2684/song-jury.git`
  (好處:之後 `git pull` 就能更新;另外 `tests/` 裡有 8 條打包自足性檢查需要 git,
  ZIP 版會誠實跳過並告訴你原因。)

**然後**:
**Windows** —— 雙擊 **`一鍵安裝.bat`**。
**Linux / macOS** —— 開終端機,`bash install.sh`。

> 💡 Windows 想直接用命令列跑的話,要帶 `-ExecutionPolicy Bypass`:
> ```powershell
> pwsh -NoProfile -ExecutionPolicy Bypass -File .\install.ps1
> ```
> 沒帶的話多數機器會被「未簽署腳本」擋下來(這個參數只影響這一次執行,
> 不會改動你系統的永久設定)。雙擊 `一鍵安裝.bat` 已經幫你帶好了。

它會自己做完這些,**中間任何一步失敗都不會中斷**,最後一次告訴你哪裡沒成功:

```
[ 1/10] 檢查並補齊基本工具(uv / git / ffmpeg)  ← 沒有就用 winget / brew / apt 幫你裝
[ 2/10] Gemini 金鑰               ← ⭐ 全程唯一要你動手的一步,問完就能放著不管
[ 3/10] 建立量測環境 .venv
[ 4/10] 建立模型環境 .venv-ml(SongEval + Audiobox)
[ 5/10] 取得 SongEval 原始碼
[ 6/10] 鎖回 torch 版本
[ 7/10] 建立分軌環境 .venv-demucs
[ 8/10] 建立新耳朵環境 .venv-audition
[ 9/10] 情緒詞典
[10/10] 自我檢查 —— 實際確認九根柱子哪些可用(含真打一次 Google API 驗金鑰)
```

> **金鑰為什麼排在最前面**:它是全程唯一需要你回答的問題。
> 放在後面的話,你去泡茶回來會發現安裝卡在那裡等輸入了半小時 —— 這是實測踩到才改的。

### 🔑 Gemini 金鑰是必要的,不是可選

**律動柱(4%)100% 靠 Gemini**,沒有金鑰那根柱子整根評不出來 →
依九柱制的定義,你的機器就**評不出有效分數**(另外還有結構/旋律/人聲/整體/曲風各缺一項)。

[**免費申請**](https://aistudio.google.com/apikey)(Google 帳號登入就能拿,免費額度個人用足夠)。
安裝時直接貼上即可;先跳過的話,之後把 `.env.example` 複製成 `.env`、
填 `GEMINI_API_KEYS=你的金鑰`,再跑一次 `-CheckOnly` 確認。

### 🎛 ffmpeg 也是必要的,不是可選

Gemini 聽歌走 API 內嵌上傳,上限約 20MB(base64 後)——**一般 WAV
(4 分鐘 PCM ≈ 40MB)必超限**,要靠 ffmpeg 自動轉 320k mp3 才進得去。
沒有 ffmpeg 的機器評 WAV 時,Gemini 餵的六個柱項會整批缺席 → 不算完整安裝,
安裝腳本會以紅字擋下並 exit 1。安裝腳本會自動幫你裝(winget / brew / apt);
自動裝失敗就手動裝好加入 PATH,再跑一次 `-CheckOnly`。

> 🔬 **分軌線體檢**(結構編曲柱 + 和聲柱,合計 26.2%)由 `分軌線檢查.py` 做,
> 兩支安裝器共用同一份邏輯。它會**印出正在做什麼**、暫時性失敗**再試一次**
> (剛裝完那幾分鐘防毒還在掃新檔,失敗多半是假的)、而且**分得出**
> 「缺套件」與「DLL/權限/快取損壞」——後者重裝 requirements 沒有用,不會叫你白做。
> 整段有預算上限,預設 900 秒,可用 `SONG_JURY_DEMUCS_PROBE_TIMEOUT` 調整
> (⛔ 填錯 —— 非數字、NaN、0、負數 —— 會明確告訴你是**設定**的問題,
> 不會被說成缺套件叫你重裝幾 GB;工具自己出錯又是另一種訊息,兩者不共用碼)。
> 它的輸出**直接寫到終端**(即時、原汁原味),安裝器判斷讀的是它寫的
> UTF-8 狀態 JSON —— 不解析中文訊息,所以換 code page 也不會判錯。
> 狀態檔的清理在**同一個 `finally`** 裡(Codex R22-P2-3:舊版寫在 try 之後 20 行,
> 中間中斷就會把隨機檔名的狀態檔留在 TEMP 裡累積);POSIX 版在這一段按 Ctrl+C
> 會**清完檔案就以 130 結束**,不會像舊版那樣清完繼續往下裝(Codex R22-P2-4)。
> 探針跑在背景再 `wait`,所以中斷是**立刻**生效的:handler 先把訊號轉給探針、
> 收屍,再以 130(INT)/ 143(TERM)結束 —— 舊版把探針放前景,bash 會把 trap
> 押到它結束才跑,只送訊號給主程序的自動化(systemd / CI / supervisor)得傻等
> 探針跑完(Codex R23-P2-2 實測等滿整整一輪)。
> ⛔ 而且整支腳本**只有一個 EXIT trap**(`cleanup_all`):shell 的 trap 不是堆疊,
> 局部再裝一個就會把全域那份蓋掉 —— 實測每跑一次就在 TEMP 留一份 `sj_step.*`
> (裡面可能有失敗命令的診斷與本機路徑),而中斷測試只掃狀態檔所以完全沒看到
> (Codex R24-P2-1)。正常、INT、TERM 三條路現在都掃「TMPDIR 必須是空的」,
> 冒煙測試那份暫存 JSON 也改成隨機私密檔名並納入同一個清理(兩個平台;
> Codex R25-P2-3:它以前用固定的 PID 檔名、只在線性路徑刪,量測跑到一半
> 被中斷就留在 TEMP)。
> ⛔ 終止探針時,群組與單一 PID 的訊號**各自送**、等待有上限、逾時升級成 KILL ——
> `群組 || 單一` 的寫法在 Git Bash 上會因為「群組 kill 回 0」而永遠不補送第二道,
> 而 Windows-native 的 python 根本沒死,接著就一路等到它自然結束
> (Codex R25-P1-2 實測等滿 60 秒;那也是**非決定性**的,所以中斷測試每個訊號跑兩輪)。
> 若是重試才成功,安裝器會給你一行黃字警告:那條線在這台機器上不穩,正式評分可能掉柱。

> 📁 順帶一提:工作鎖與 Gemini 冷卻狀態放在**使用者全域目錄**
> (Windows:`%LOCALAPPDATA%\song-jury`;Linux/macOS:`~/.local/state/song-jury`),
> 不在工具資料夾裡 —— **同一位 OS 使用者**存幾份副本,互斥與金鑰冷卻都是共用的。
> ⚠️ 誠實邊界:不同 OS 帳號(例如登入使用者 vs 排程服務)或不同機器,
> 同時評同一個共享音檔仍會互踩中間檔,不要那樣用。
> 裡面只有 0 byte 的鎖檔與一個小 JSON,可放心無視。

最後印出來的長這樣 —— **它不會只說「安裝成功」,而是逐柱告訴你能不能算分**:

```
      柱             權重    狀態
      ────────────────────────────────────────────────────────
      詞            25.3%   完整
      人聲演唱      15.2%   部分 —— 缺 SingMOS 聽感
      和聲          13.6%   完整
      結構與編曲    12.6%   缺項(整柱不計)
      ...
      ⛔ 安裝不完整 —— 有 12.6% 的權重整根缺席,這台機器目前【評不出有效分數】。
```

### ⛔ 要裝就要全部裝齊

**九柱制的滿分定義是「九根柱子都在」。少一根就是換了一把尺** ——
程式仍會把剩下的柱重新歸一化算出一個數字,但那個數字**不可與別人互比、不可拿去排行、
不可當作品的評測結果**。所以報告與 JSON 都會被打上「⛔ 不完整評測」的標記,不會讓它偽裝成正常分數。

裝到一半斷線很正常(要下載好幾 GB)。**直接重跑同一個安裝檔**,已經裝好的不會重裝,
補到自我檢查印出「✅ 九柱齊全、細項無缺」為止。
事後想再確認一次:`./install.ps1 -CheckOnly` 或 `bash install.sh --check-only`(什麼都不會裝)。

> 📄 單獨驗一份報告:`python 驗證報告.py 某某_評審團.json`(相容模式,會印
> `VERIFY_OK_LEGACY …;來源身分證據=<等級>`)。要它當「本輪新產物」的證據,
> 三個開關都要帶:`--newer-than <epoch> --require-contract --require-identity` ——
> ⛔ 相容可讀 ≠ 新產物證據(Codex R21-P2-4:舊版不管怎麼呼叫都印「本輪新產物」)。
> ⛔ `--newer-than` 只收**有限**數字:`nan` 會讓 mtime 比較永遠不成立,
> 一份一天前的舊報告照樣被蓋上「本輪新產物」(Codex R22-P2-2 實測,`-inf` 同理)。
> ⛔ `--require-identity` 與 `--allow-declared-downgrade` **互斥**,同時給會直接
> `VERIFY_BAD`(Codex R23-P2-1:舊版讓比較鬆的那個無聲勝出,你以為要求了最強證據)。
> ⛔ **不認得的參數一律 `VERIFY_BAD`**:`--require-identit` 少打一個 y 在舊版會靜靜
> 退成 rc=0 的相容驗證,只看退出碼的自動化把「參數打錯」當成功(Codex R24-P2-2)。
要「連模型下載/載入/推論都來真的」的完整證明:`./install.ps1 -VerifyModels` 或
`bash install.sh --verify-models` —— 它會用一個唯一檔名實跑一遍九柱(強迫每個模型
真的推論一次,首次會下載數 GB,很久),再用 `驗證報告.py` 獨立拆 JSON 驗完整性。
(整條流程收在 `完整驗證.py` 裡,安裝器只讀退出碼 —— 這樣 Ctrl+C 一定清得乾淨、
中斷與失敗也分得開;shell 的 `finally`/`trap` 在這兩件事上都靠不住。)

> 📌 `評審團.py` 自己的退出碼:**0** 完整評測、**2** 報告已發布但缺柱、
> **4** 評測完成但來源快照沒收乾淨(TEMP 裡留了一份音訊,見上面)、其他 = 失敗。
>
> ⭐ **4 是「清理問題」不是「評測失敗」**,所以三個下游都會**照樣讀報告**
> (Codex R25-P1-1:舊版把 4 當一般失敗 —— 批次與網頁把一份跑了幾十分鐘的
> 有效評測整份丟掉,完整驗證還把 4 洗成 1、連裁判都不跑):
> · 批次:收進表、該首標成 `⚠ DIRTY`,而且**批次結尾會再列一次完整路徑**
>   (Codex R26-P1-2:只印在即時輸出的話,幾十首之後就被推走了,而那些目錄裡
>   是一整份音訊);殘留狀態也寫進 store,`--skip-existing` 下次照樣提醒得到;
> · 網頁版:照樣顯示成績表,並在說明區掛上殘留路徑;
> · `完整驗證.py`:仍跑獨立裁判,通過印 `VERIFY_DIRTY`(⛔ **絕不印 VERIFY_OK**)
>   並保留退出碼 4;報告本身不合格才回 1。
> ⛔ 但 4 會蓋掉原本的 2,所以**完整性一律讀報告裡的 `pillar_totals.完整評測`**,
> 不可以因為「碼是 4」就當成完整評測。

**安裝器的退出碼(自動化請照這個判;兩個平台同一份契約)**:

| 碼 | 意思 | 該怎麼辦 |
|:--:|---|---|
| **0** | 九柱齊全、金鑰**驗證通過**、冒煙測試過 | 可以開始評分 |
| **1** | 有步驟失敗、缺柱、缺 ffmpeg,或 `-VerifyModels` 沒過 | 看上面的紅字補齊後重跑 |
| **3** | 元件都齊,但**金鑰有效性未能驗證**(全部限流中 / 網路 / TLS) | 不是壞掉,但也還不能宣稱可用;恢復後重跑 `-CheckOnly` |
| **5** | **金鑰政策無效**(拒絕名單格式錯、`.env` 來源可疑) | ⛔ 這不是「沒填金鑰」—— 去申請新 key 沒有用,照訊息修設定 |
| **64** | 參數打錯(例如 `-VerifyModels` 拼錯) | 照提示改參數;⛔ 不會靜默當成普通安裝 |
| **124** | `-VerifyModels` **逾時**(已中止整棵程序樹) | 首次下載模型可能不夠久 —— 加長 `SONG_JURY_VERIFY_TIMEOUT` 再試 |
| **130** | `-VerifyModels` 被**使用者中斷**(Ctrl+C) | 不是安裝失敗;要驗請重跑 |

**這七個碼在 Windows 與 Linux/macOS 完全一樣**,`一鍵安裝.bat` 也原樣傳出
(它只在非 0 時 `pause` 給人看,不吃掉退出碼)。124 / 130 是**故意不折成 1** 的 ——
自動化必須分得出「逾時」「使用者取消」與「真的裝壞」,兩個平台不能各有一套
(Codex R17-2 抓到過:sh 傳 130、PowerShell 折成 1)。

> ⚠️ 唯一會被折疊的是完整驗證的 **2**(九柱跑完但缺柱):那**就是**安裝不完整,
> 所以安裝器回 1。`評審團.py` 自己另有一套碼:**0=完整評測、2=報告已發布但缺柱、其他=失敗**。

**⛔ 上面那張表是「安裝器對外」的碼。內部 helper 各有自己的碼,不共用命名空間**
(Codex R19-4:混用會讓人拿到錯的修復指示):
> · `分軌線檢查.py`:0=可用、1=缺套件、2=其他不可用、**3=設定錯誤**、**4=工具自己出錯**
> · `完整驗證.py`:0=過、1=沒過、2=缺柱、**3=設定錯誤**、124=逾時、130=使用者中斷
> 安裝器會把這些翻成自己的訊息;對外的 **3 永遠只代表「金鑰未能驗證」**。

> 🔒 `分軌線檢查.py` 另外會寫一份 `--status-json`(UTF-8、原子寫入、隨機私密檔名、
> 用完即刪)給安裝器判斷**種類**。⛔ 它只是診斷補充:**與實際退出碼不一致就整份忽略**,
> 而且永遠不能把失敗說成成功(Codex R20-P2-1:殘留或被改過的檔案曾能把 rc=4
> 說成「設定值有問題」,把人導去改一個沒問題的環境變數)。
>
> 驗證由**獨立的** `狀態驗證.py` 做(⛔ 驗證器不可以是被驗的那支程式自己):
> `rc` 必須是整數且等於實際退出碼、`ok` 必須是布林且與退出碼相符、
> `kind` 必須落在**該退出碼的合法集合**(0↔ok、1↔missing_module、
> 2↔timeout/launch/import、3↔config_error、4↔internal_error)、
> `recovered` 必須是布林且成套(只可能出現在 `rc=0, kind=ok, tries>=2,
> first_error 非空`)。任一條不符就整份忽略並印出原因。
> ⚠️ 威脅模型:同一個 OS 使用者本來就能改腳本,這裡不做密碼學真實性 ——
> 這套契約處理的是**殘留、競速、半份檔案、結構性矛盾**。

其他開關(⚠️ **都不是評測用的**,只給「先確認機器跑得動」用):
`-SkipML` / `--skip-ml` 只裝量測+報告 —— 這樣裝**評不出有效分數**,測完請補齊;
`-NoAutoTools` / `--no-auto-tools` 不要自動幫你裝系統工具。

## 用法

> ⚠️ **一定要用 `.venv` 裡的 python**,不能打裸 `python` —— 所有相依都裝在 `.venv`,
> 用系統 python 會 `ModuleNotFoundError`。下面每一行都已經寫成正確形式。

```bash
# Windows(PowerShell)
.venv\Scripts\python.exe 評審團.py "<SUNO/YouTube 連結 或 音檔路徑>"   # 九柱音訊評測 → 歌名_評審團.json
.venv\Scripts\python.exe 情感弧線.py 歌詞.txt                          # 情感弧線圖 → _情感弧線.png
.venv\Scripts\python.exe 報告轉PDF.py 報告.md                          # 報告 md → PDF
.venv\Scripts\python.exe 轉PNG.py    報告.pdf                          # PDF → 全長 PNG
```

```bash
# Linux / macOS
.venv/bin/python 評審團.py "<SUNO/YouTube 連結 或 音檔路徑>"
.venv/bin/python 情感弧線.py 歌詞.txt
.venv/bin/python 報告轉PDF.py 報告.md
.venv/bin/python 轉PNG.py    報告.pdf
```

**詞柱**不是程式跑的:把歌詞交給對話中的 AI,說「依評詞標準評詞」—— AI 讀 `評詞標準.md` 與
`rubrics/` 底下對應語言的尺照辦。

`評審團.py` 負責「評一首歌的曲側八柱」;PK / 抽卡比較由 AI 編排(跑多首 + 綜合),不是程式職責。

./run_web.ps1        # Windows

```

報告的骨架是**兩層**:先一張**九柱總覽**(每柱評什麼、占多少、拿幾分、一句話),
再**逐柱攤開細項**(細項 | 占柱內 % | 分數 | 解讀)。三條硬規矩:

- ⛔ **沒有解讀的分數 = 黑盒,不准出報告** —— 每個數字右邊都要有一句人話。
- ⛔ **解讀主文寫這首歌這一項的具體狀態**(帶實測值),定義與免責放括號擺句尾;
  「色彩多元」這種放到別首歌也成立的話 = 不合格。
- ⛔ **不腦補因果** —— 沒有數據支持的「因為…所以…」一律刪掉。

報告最後還有**名詞小註**(給第一次讀的人)、**親聽檢查清單**(人耳要去確認什麼)、
**合議庭裁決**(把量測與模型吵架的地方攤開,裁量權留給人)。

repo 附四首**作者自己的 SUNO 作品**(同意公開散布),中/英/日/韓各一、都帶歌詞 —— 裝完立刻就能試,四把語言尺各有一首可以對照:

## 詞柱:四把語言尺

歌詞語言決定用哪把尺(判定順序 **韓 → 日 → 中 → 英**;日文含漢字須排在中文前):

| 語言 | 尺 | 維度數 |
|---|---|:--:|
| 中文(國/粵/台/客) | `rubrics/ZH_lyric_rubric_v5.md` | 7 |
| 英文 | `rubrics/EN_lyric_rubric_v2.md` | 6 |
| 日文 | `rubrics/JA_lyric_rubric_v3.md` | 6 |
| 韓文 | `rubrics/KO_lyric_rubric_v4.md` | 7 |

⛔ **四把尺絕不混讀** —— 它們的軸互斥(韓文尺明文廢掉日文的音高重音與中文的倒字)。
⛔ **跨語言 PK 禁止** —— 維度數與軸不可共量。

**Craft / Reach 雙分**:「寫得好不好」與「傳不傳得開」分開給,**明文禁止平均**。
一首歌可能作品分高、爆款分低(藝術性強但小眾),或反過來。

**情感框架**(AI 沒有感受,評情感只准交證據,禁「我覺得很感人」):
中文尺走情感三支柱(客觀對應物 / 張力管理 / 情感弧線儀)、英日韓尺各有對應框架。

**題材選尺**:嘻哈看多押內韻、民謠白描不算說教、古風文雅凝練(口語反而扣分)、
搖滾態度宣言是慣例不扣、洗腦向疊詞是本體 —— 防曲風偏見。

四把尺各經**八家模型五輪對抗審查**定版;理論靠山、判準與誠實條款寫在各尺內。

## 測試

```bash
pip install -r requirements-dev.txt
python -m pytest tests -q          # 512 條(約 6 分;含真子程序樹、兩支安裝器 × 兩個 PowerShell 引擎的退出碼矩陣、
                                   #   「進度要即時看得到」的真時序測試、比較器行為)
python tests/變異驗證.py            # 證明測試不是裝飾品
```

**測試刻意不需要那四個重量級環境**(torch / demucs / SongEval 合計十幾 GB)——
只要 `pytest + numpy` 就跑得完。因為這個專案出過的 bug 幾乎全部都在**接線與邏輯**上,
不在模型推論裡:打包漏檔、取值鍵名寫錯、快取撞名、分數沒夾範圍、缺柱被當成正常分數、
失敗時偷用舊報告。每一條測試都對應一個**真的發生過**的事故。

### 變異驗證:憑什麼相信這些測試有用

`tests/變異驗證.py` 會把每個已修好的缺陷**塞回程式裡**,跑對應的測試,確認它真的失敗,再還原:

```
[1/230] ✅ 抓到了:切窗漏掉最後一個完整窗(40s 只分析 1 個窗)
[2/230] ✅ 抓到了:Gemini 分數不夾範圍(M1:99 → 990/100)
[3/230] ✅ 抓到了:Gemini 總分取錯鍵名(整關被靜默丟掉)
[4/230] ✅ 抓到了:快取不驗身分(同名不同曲會讀到別首歌的分軌)
...
  ✅ 230 條真實缺陷全部會被測試抓到
```

⛔ **一條測試若在缺陷被塞回去之後仍然通過,那條測試就是裝飾品。**
第一次跑這支的時候,它就抓出我自己有兩條測試是裝飾品 —— 這正是它存在的理由。
CI 會獨立跑它,讓「測試有沒有效」本身也被自動檢查。

它也拒絕把「沒驗到」講成「通過」:目標測試被 skip(平台不支援)、
目標測試**選不到**(改過名字)、變異字串找不到(程式重構過)、
`git` 本身故障(index.lock/唯讀)——都會單獨標示或直接算失敗,不會混進通過率裡。

平台專屬的缺陷由**兩個** CI 工作各自負責:ubuntu 跑全部(POSIX 語意那幾條在那裡驗),
Windows 跑 `--only-platform win32`(Job Object、venv layout、PowerShell 退出碼那幾條)。
⛔ 這是刻意的:只有 ubuntu 的話,「兩平台合起來全覆蓋」其實只是
「CI + 某次人工執行」,不是每次 commit 的證據。

## 誠實條款

- **不是客觀真理**,是可辯護的診斷判斷;讀差距,別讀絕對值。
- **SongEval / Audiobox 有品味傾向**:實測它們給 AI 生成音樂的分**高於**專業得獎作品
  (對照實驗已排除音檔品質因素)→ 這兩具只可**同類池內相對比較**,不當絕對品質讀,報告會標註。
- **詞曲咬合目前無可靠儀器**(候選未過判別考,誠實空缺)。
- **情感弧線儀絕對值不可信**(詞庫盲於反諷),只看段落間相對移動。
- **SUNO 連結評的是未後製原始版**,與後製成品不可互比。
- **終審是聽眾** —— 發佈後的完播、分享、被引用的句子,勝過本標準的一切判定。
